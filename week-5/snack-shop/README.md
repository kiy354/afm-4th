# 과자상점 — 과자 쇼핑몰

과자를 고르고, 장바구니에 담고, 주문하고, **토스페이먼츠로 결제**하고, 주문을 조회하는 쇼핑몰입니다. (테스트 키라 실제로 돈은 나가지 않습니다)
회원가입하면 주문서에 이름·전화번호가 자동으로 채워지고, 마이페이지에서 주문내역을 모아볼 수 있습니다. 비회원 주문도 됩니다.

**배포 주소: https://afm-snack-shop.vercel.app**

- 프론트엔드: 단일 `index.html` (CDN React 18 · Babel Standalone · Tailwind)
- 백엔드: 단일 `server.js` (Express 5)
- DB: Supabase PostgreSQL — `snack_products` · `snack_orders` · `snack_order_items` · `snack_users`
- 인증: 비밀번호는 bcrypt 해시로 저장, 로그인 상태는 JWT(7일)
- 결제: 토스페이먼츠 결제위젯 v2 (주문 → 결제창 → 서버 승인)

## 실행

```powershell
cd week-5/snack-shop
npm install
Copy-Item .env.example .env   # DATABASE_URL, JWT_SECRET, TOSS_CLIENT_KEY, TOSS_SECRET_KEY, PAYMENT_MODE 채우기
npm start                      # http://localhost:3200
```

테이블은 서버가 처음 요청을 받을 때 만들고, 상품 테이블이 비어 있으면 과자 18종을 넣습니다.

## 구현하면서 해결한 문제

### 1. 금액은 서버가 계산한다
장바구니는 브라우저(`localStorage`)에 **상품 id와 수량만** 저장합니다. 가격까지 저장하면
가격이 바뀌었을 때 옛 가격이 남고, 누군가 값을 고쳐 1원에 주문할 수도 있습니다.
그래서 장바구니·주문서 화면은 `/api/cart/quote`로, 주문은 `/api/orders`에서 **DB의 현재 가격으로** 다시 계산합니다.

### 2. 동시에 주문이 몰려도 재고 이상 팔지 않는다 — 트랜잭션 + `FOR UPDATE`
"재고 확인 → 차감" 사이에 다른 주문이 끼어들면 같은 재고를 두 번 팔 수 있습니다.
주문 전체를 `BEGIN … COMMIT`으로 묶고, 상품 행을 `SELECT … FOR UPDATE`로 잠가서
먼저 온 주문이 끝날 때까지 다음 주문이 기다리게 했습니다.
여러 상품을 잠글 때는 **id 순서로** 잠가 두 주문이 서로를 기다리는 교착(deadlock)을 피합니다.
또 `stock` 컬럼에 `CHECK (stock >= 0)`을 걸어, 코드가 실수해도 DB가 음수 재고를 거부합니다.

> 재고 5개인 상품에 2개씩 5건을 **동시에** 주문해 확인했습니다 → 2건 성공, 3건 "n개까지 주문할 수 있습니다", 남은 재고 1개.

### 3. 주문 당시의 상품명·가격을 복사해 둔다
`snack_order_items`에 상품 id뿐 아니라 이름·가격도 저장합니다. 나중에 상품 가격이 바뀌거나
이름이 바뀌어도 지난 주문 내역은 주문한 그대로 보여야 하기 때문입니다.

### 4. 주문번호는 추측하기 어렵게, 조회는 전화번호까지
주문번호를 `1, 2, 3…`으로 주면 남의 주문을 쉽게 들춰볼 수 있습니다.
`날짜-무작위6자리`(예: `20261006-482913`)로 만들고, 조회할 때는 **주문 때 쓴 전화번호까지 맞아야** 보여줍니다.
번호가 없는 경우와 전화번호가 틀린 경우는 같은 문구로 답합니다.
무작위 번호가 우연히 겹치면(UNIQUE 위반) `SAVEPOINT`로 그 INSERT만 되돌리고 번호를 바꿔 다시 시도합니다.

### 5. 정렬·검색에서 SQL 주입 막기
`ORDER BY`에는 `$1` 같은 파라미터를 쓸 수 없어서, 사용자가 보낸 `sort` 값을 SQL에 그대로 넣으면 위험합니다.
정해진 목록(`SORTS`)에서만 골라 쓰고, 모르는 값이면 인기순으로 처리합니다.
검색어의 `%`·`_`는 LIKE의 와일드카드라 이스케이프해서 글자 그대로 찾게 했습니다 ("70%" 검색 → 다크 초콜릿 70%만).

### 6. 주문 완료 화면 대신 장바구니로 가던 버그
주문서에는 "장바구니가 비어 있으면 장바구니 화면으로 보내기" 처리가 있었는데, 주문에 성공해 장바구니를 비우는
순간에도 이 처리가 실행되어 완료 화면 이동을 덮어썼습니다. **주문서에 처음 들어올 때만** 검사하도록 바꿨습니다.
(커뮤니티 앱의 "로그인 후 원래 화면으로" 버그와 같은 유형 — 화면 이동이 두 곳에서 일어나면 나중 것이 이깁니다)

### 7. 회원 주문과 비회원 주문을 함께 받는다
`snack_orders`에 `user_id` 컬럼을 추가했습니다. 비회원 주문은 `NULL`이고, 회원이 탈퇴해도 주문 기록은
남아야 하므로 `ON DELETE SET NULL`로 걸었습니다. 회원 기능이 주문 테이블보다 나중에 생겼기 때문에
`ALTER TABLE … ADD COLUMN IF NOT EXISTS`로 붙여서, 이미 배포된 DB에도 그대로 적용됩니다.

주문 API는 로그인이 **선택**입니다(`optionalAuth`). 다만 토큰을 보냈는데 만료됐다면 조용히 비회원 주문으로
바꾸지 않고 401로 알려 다시 로그인시킵니다 — 회원으로 주문했다고 생각했는데 내 주문내역에 안 보이는 일을 막기 위해서입니다.

### 8. 주문서에서 로그인하면 주문서로 돌아오고, 이름·전화번호가 채워진다
비회원으로 주문서까지 왔다가 로그인(또는 회원가입)하면 다시 주문서로 돌아옵니다. 이동은 커뮤니티 앱에서 배운 대로
**라우트 가드 한 곳에서만** 합니다. 주문서 컴포넌트에 `key={user.id}`를 줘서, 로그인 직후 컴포넌트를 새로 만들어
가입 때 적은 이름·전화번호가 채워지게 했습니다.

### 9. 내 주문내역은 쿼리 두 번으로
주문 목록을 가져온 뒤 주문마다 상품을 따로 조회하면 주문 수만큼 쿼리가 나갑니다(N+1 문제).
주문 id 목록으로 `order_id = ANY($1)` 한 번에 상품을 가져와 서버에서 주문별로 나눴습니다.

### 10. 상품 사진 대신 이모지 + 그라데이션
이미지 파일 없이도 쇼핑몰처럼 보이도록, 상품마다 이모지와 배경색을 DB에 두고 카드로 그렸습니다.

### 11. 결제는 "주문(결제 대기) → 결제창 → 서버 승인" 세 단계
`POST /api/orders`는 이제 주문을 `pending`(결제 대기)으로 만들고 재고를 잡아 둡니다. 결제 화면(`#/orders/:주문번호/pay`)에서
토스 결제위젯이 결제수단·약관을 그리고, 결제가 끝나면 토스가 `?payment=success&paymentKey=…&orderId=…&amount=…`로 돌려보냅니다.
이때 **브라우저가 아니라 서버가** `/api/payments/confirm`에서 시크릿 키로 토스 승인 API를 호출해야 결제가 확정됩니다.
승인 전에 돌아온 금액이 DB의 주문 금액과 같은지 확인합니다 — 다르면 위변조로 보고 주문을 실패 처리합니다.
장바구니는 결제가 끝난 뒤에 비웁니다(결제를 포기해도 장바구니는 남도록).

### 12. 결제되지 않은 주문은 재고를 돌려준다
주문 시점에 재고를 잡아 두므로, 결제가 안 되면 재고를 되돌려야 합니다.
- 결제창에서 실패·취소 → `failUrl`로 돌아오면 `/cancel`로 주문을 `canceled` 처리
- 토스가 승인을 거절(4xx) → `failed`
- 결제하지 않고 떠남 → 주문 후 **30분**이 지나면 `expired`. 크론 대신 다음 주문이 들어올 때 정리합니다.

어느 경우든 같은 함수(`closeUnpaidOrder`)가 상태를 바꾸고 재고를 복구하며, 주문 생성과 같은 규칙으로 상품 행을 **id 순서로** 잠급니다.
승인 처리 중인 주문은 행을 잠그고(`FOR UPDATE`) 만료 정리는 `SKIP LOCKED`로 건너뛰어, 결제 승인과 만료가 겹쳐도 재고가 두 번 돌아오지 않습니다.
토스 서버 오류(5xx·시간 초과)는 결과를 알 수 없으므로 주문을 `pending`으로 두고 다시 시도하게 합니다.

### 13. 배포 사이트와 DB를 같이 쓰므로 컬럼 기본값은 그대로 둔다
`snack_orders.status`의 기본값은 `'paid'`입니다. 결제 기능 이전 코드(배포된 버전)는 status 없이 INSERT 하기 때문에,
기본값을 `'pending'`으로 바꾸면 **배포 사이트의 주문이 모두 결제 대기가 되어 30분 뒤 취소**됩니다.
그래서 기본값은 바꾸지 않고, 새 코드가 INSERT 할 때 `'pending'`을 명시합니다. 결제 정보 컬럼은 `ADD COLUMN IF NOT EXISTS`로만 붙였습니다.

### 14. 비회원 결제와 본인 확인
비회원도 결제할 수 있도록 토스 `customerKey`는 회원이면 `snack_users.customer_key`(UUID), 비회원이면 `ANONYMOUS`를 씁니다.
결제 승인은 로그인 없이 받습니다 — `paymentKey`는 실제 결제창을 통과해야만 생기고 토스가 주문번호·금액과 함께 검증하기 때문입니다.
반대로 주문 취소는 누구나 남의 주문을 취소할 수 없게, 주문 조회와 같은 방식으로 **전화번호가 맞아야** 합니다.
결제창으로 페이지를 떠났다 돌아오므로 주문번호·전화번호는 `sessionStorage`에 잠깐 둡니다.

### 15. 마이페이지에는 결제 완료 주문만
`/api/me/orders`는 `status = 'paid'`인 주문만 돌려줍니다. 결제 대기·실패·취소 주문은 주문조회(`#/lookup`)에서 상태와 함께 보입니다.
주문 상세에는 결제수단·결제일시·토스 영수증 링크를 보여줍니다.

> 검증: 테스트 계정으로 회원가입 → 로그인 → 장바구니 → 주문서 → 결제위젯 → 토스 결제창까지 진행했습니다(`screenshots/payment/`).
> 토스 테스트 상점도 마지막 인증(카드사 앱·토스 앱 QR)은 실제 사람이 해야 해서 그 단계는 자동화하지 않았습니다.
> 결제창 취소 → 주문 취소·재고 복구, 금액 위조 → 실패 처리·재고 복구, 30분 경과 → 만료·재고 복구, 가짜 paymentKey → 토스 거절은 확인했습니다.

### 16. 사람 인증 없이 끝까지 시험하는 테스트 결제 모드
토스 테스트 상점도 마지막 단계는 실제 사람의 인증(카드사 앱·토스 앱 QR, 카드번호 입력)이 필요하고, 국내 테스트 전용 카드번호도 없습니다.
그래서 결제 흐름 전체를 시험할 수 있도록 `.env`의 `PAYMENT_MODE=test`로 켜는 **테스트 결제창**을 만들었습니다.

- 결제 화면에 토스 위젯 대신 테스트 결제창(카드·간편결제·계좌이체)과 "결제 실패 시나리오" 버튼이 나옵니다.
- 서버의 `/api/payments/test`는 토스 승인 API 호출만 건너뛰고, 주문 잠금·금액 확인·상태 변경·재고 복구는
  토스 결제와 **같은 함수(`settleOrder`)**를 씁니다. 그래서 테스트 결제로 확인한 흐름이 토스 결제에도 그대로 적용됩니다.
- 비회원 주문도 있으므로 주문 조회처럼 **전화번호**로 본인 확인을 합니다.
- `PAYMENT_MODE`가 비어 있으면 토스 모드이고, 테스트 결제 API는 404입니다. 배포 환경에서 실수로 "공짜 결제"가 열리지 않도록
  테스트 모드는 명시해야만 켜집니다.
- 처음엔 테스트 승인 시각을 Node의 `new Date()`로 넣었더니, 주문 시각(DB의 `now()`)보다 **결제 시각이 앞서는** 일이 생겼습니다
  (PC 시계와 DB 시계가 20초쯤 달랐음). 같은 화면에 함께 보이는 시각은 같은 시계를 써야 해서 `COALESCE($4, now())`로 DB 시계를 쓰게 했습니다.

> 검증(`screenshots/payment-test-mode/`): 로그인 → 장바구니 → 주문서 → 테스트 결제창 → 결제 완료 화면 → 마이페이지 결제 내역,
> 실패 시나리오 → 주문 실패·재고 복구·장바구니 유지를 브라우저로 확인했습니다.

### 17. 결제 금액은 승인 직전에 DB에서 다시 계산하고, 승인번호를 저장한다
결제창에서 돌아온 금액을 주문 때 저장해 둔 합계(`total`)와만 비교하면, 저장값 자체가 어긋났을 때는 잡지 못합니다.
그래서 승인 직전에 **주문 상품 내역(`snack_order_items`)으로 상품 금액·배송비를 다시 계산**해
"요청 금액 = 재계산 금액 = 저장된 합계"가 모두 맞을 때만 승인합니다. 하나라도 다르면 주문을 실패 처리하고 재고를 돌려주며,
서버 로그에 `요청 / 재계산 / 저장값` 세 숫자를 남깁니다.

승인 뒤에도 결제사가 **실제로 승인한 금액**(토스 `totalAmount`, 테스트 결제는 요청 금액)을 재계산 금액과 한 번 더 대조하고,
다르면 결제를 취소합니다. 통과하면 승인번호를 `snack_orders.approve_no`에 저장해 완료 화면·마이페이지·주문조회에 보여줍니다.
토스 카드 결제는 카드사 승인번호(`card.approveNo`), 테스트 결제는 실제 번호와 구분되게 `T` + 8자리입니다.
(토스 간편결제·계좌이체는 승인번호를 주지 않아 비어 있을 수 있습니다.)

> 검증(`screenshots/payment-100won/`): 100원짜리 `[테스트] 결제 테스트 과자`로 로그인 → 장바구니 → 주문서 → 테스트 결제 →
> 완료 화면(승인번호 `T69881051`) → 마이페이지까지 진행하고 DB에 `approve_no`가 저장된 것을 확인했습니다.
> 같은 상품으로 새 주문을 만든 뒤 개발자도구 콘솔에서 금액을 10원으로 바꿔 보내면
> `400 결제 금액이 주문 금액과 일치하지 않습니다` → 주문 실패·재고 복구, 이후 정상 금액으로 다시 보내도 `409 이미 처리된 주문`으로 막힙니다.

## 배포 (Vercel)

```powershell
npx vercel env add DATABASE_URL production
npx vercel env add JWT_SECRET production   # 로컬과 다른 값으로
npx vercel env add TOSS_CLIENT_KEY production
npx vercel env add TOSS_SECRET_KEY production
npx vercel --prod
```

Vercel 팀 `afm-4`의 프로젝트 `afm-snack-shop`. `.vercelignore`로 `.env`·`node_modules`·`screenshots`는 업로드하지 않습니다.
로컬과 배포 사이트가 **같은 Supabase DB**를 쓰므로, 로컬에서 테스트로 주문하면 배포 사이트 재고도 줄어듭니다.
